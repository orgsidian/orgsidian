## Scope Fence (read first)

This story builds the **index write-path** — the first code that turns real `.org` files into rows — and the **first-launch/Settings Vault designation surface** on top of it. It is the largest story in Epic 3 and touches five crates + the frontend, so the boundaries below are load-bearing.

**The deliverable is:**

1. **`orgsidian-index` — a parser-agnostic, transactional sync engine** (`src/sync.rs`) plus an **index-identity guard** (`src/identity.rs`, `application_id` stamp + foreign-file/version mismatch detection). The sync engine maps *index-native input structs* (NOT `orgsidian_parser::Document`) into the `files`/`headlines`/`tags`/`properties`/`clock_entries`/`links` tables **and** the two external-content FTS5 tables, honoring the schema's mandated FTS `'delete'`-row pairing and deletion order **inside one transaction per file**. It ships an incremental upsert keyed on `(mtime_ns, size_bytes)` and a delete path. It grows `IndexError` and re-exports the new surface. It gets **NO** `orgsidian-parser` dependency.
2. **`orgsidian-vault` — recursive `.org` discovery** (`src/path.rs`): walk a designated root, return the `.org` file list (skipping `.orgsidian/`), canonicalize the vault root once, define the vault-relative path form, and skip non-UTF-8 names. Plus **wire `clean_orphan_temp_files` into the vault-open flow** (the integration point `lib.rs:8-9` names).
3. **`orgsidian-core` — the scan orchestrator** (`src/index/` façade + `src/index/scan.rs`): the ONLY place both `parser` and `index` are visible. It walks (via vault), reads each file, `parser::analyze()`s it, **maps `Document` → the index crate's sync-input structs**, submits **one writer transaction per 100-file checkpoint** via Story 3.5's `IndexWriter::execute`, counts errors/quarantines, emits progress through a **caller-supplied callback** (no `tauri` dep in core), and honors an **`Arc<AtomicBool>` cancel flag** checked at checkpoint boundaries. Adds the third cross-crate LEAF edge (`orgsidian-core` → `orgsidian-index`). Owns the `designate_vault` / `cancel_scan` domain functions and index-handle lifecycle.
4. **`orgsidian-shell-app` — the two Tauri commands** `designate_vault(path)` / `cancel_index_scan()` (Rust `snake_case` handlers → camelCase TS), the **first specta event** `IndexProgress { current, total, errors }` (declared via `collect_events!`, emitted via the generated handle), the **managed state** holding the index handle + cancel flag, persistence of the designated path to `GlobalSettings.recent_vaults` + `vault_meta`, and regenerated TS bindings.
5. **`shell-ui` — the Vault designation surface**: `components/settings/VaultPicker.tsx` (folder picker via `@tauri-apps/plugin-dialog`) + a **non-modal progress component** consuming `events.indexProgress.listen`, rendering "N of M files indexed, X errors" + a Cancel button, following the LD-42 non-modal + status-hairline idiom.

**It is NOT:**

- **NOT a parser edge from `orgsidian-index`.** `orgsidian-index` is a LEAF whose only permitted wrapper is `orgsidian-core` (deny.toml:193-194); it may not depend on `orgsidian-parser` (that would make it a second wrapper of the parser leaf — banned). So the `Document`→rows mapping lives in **`orgsidian-core`**, and the index crate's sync API takes plain, parser-agnostic input (Dev Note 1). The architecture's `orgsidian-index::sync::incremental` reference (architecture.md:1121) is honored as an index-native sync module; the parser coupling stays in core.
- **NOT the query/read API** (Epics 7/8, frozen in Epic 6). No `src/query/`, no `IndexQuery` trait, no agenda/search/backlink `SELECT`s. The scan is a pure **write** path. Reads in tests use trivial `SELECT count(*)`/`SELECT` assertions, not a domain query surface.
- **NOT editing the frozen index seams.** `crates/orgsidian-index/src/connection.rs` (`open`, `apply_schema`, LD-4 PRAGMAs) and `src/migrations.rs` (`migrate`, sole migration site) are **consumed, not modified**. The `application_id` guard is a **new** `identity.rs` function invoked by the vault-index open path, **not** folded into `open()` (same discipline Stories 3.4/3.5 kept — `tests/schema.rs`/`tests/migrations.rs` must pass byte-unchanged). `migrations/0001_initial-schema.sql` is **not** edited — the schema is already complete for 3.6; the sync engine populates it.
- **NOT the `notify-rs` watcher.** `orgsidian-watcher` stays a stub (Epic 5, Story 5.1). This story does **not** subscribe to filesystem events, debounce, or handle live external edits. The scan is a one-shot walk; session-time incremental re-index is Epic 5's job. Do not add `notify` anywhere.
- **NOT the app-launch auto-open flow.** Per maintainer decision at story creation, the epic AC "subsequent launches with an unchanged Vault open the cached index in <1s" is delivered here as the **mechanism** only: re-invoking `designate_vault` on an unchanged, already-indexed vault does near-zero work (every file's `(mtime_ns, size_bytes)` matches → skipped) and the identity guard passes, so it returns fast. Wiring this into a launch-time "reopen last vault without a picker" path is **Epic 6 onboarding** (StarterVaultPicker, Story 6.2). This story does not add a startup route or auto-open.
- **NOT the Starter Vault generators or onboarding coaching.** Personal GTD / Student / Freelancer content generation is Story 6.1; the `StarterVaultPicker.tsx` that routes into this story's `designateVault` flow is Story 6.2; the Empty card + coaching is Story 11.1. This story ships only the plain "designate an existing `.org` folder" surface (`VaultPicker.tsx` per the FR-15 table) that those later stories consume.
- **NOT the status-bar / Today-Dashboard integration.** There is no status bar (Epic 6/7) or Today Dashboard (Epic 7) yet. The progress UI is a self-contained non-modal component inside the designation surface, not the ambient status-bar hairline the UX spec describes for the finished app (ux:1040-1049). Wiring progress into the status bar + Today is Epic 6/7.
- **NOT the CLI `index` commands.** `orgsidian index {init|rebuild|stats|integrity}` is Story 3.7. This story ships the scan engine those commands will call, but adds **no** `orgsidian-cli` code.
- **NOT `zustand` or a new state library.** shell-ui has none installed; progress state is local React (`useState` + the event listener). Do not add a store.
- **NOT sentinel turf.** Byte-untouched: every `crates/*/tests/anchor.rs`, `crates/orgsidian-parser/` (consumed via the core façade only), `crates/orgsidian-watcher/`, the frozen `orgsidian-index` seams above, `.github/workflows/*`, `architecture.md` (process archive — record LD deviations as deferred-work rows, do not edit; Dev Note 8). `deny.toml` is touched only if a real duplicate-version ban fires (unlikely — `walkdir` is already in the lock), and then only with a matching ledger row.

### AC2 — `orgsidian-index`: a parser-agnostic transactional sync engine + FTS pairing + identity guard.

- **`src/sync.rs` — index-native input types.** Define plain structs the sync engine consumes, carrying no `orgsidian-parser` type (Dev Note 1): e.g. `FileIndexInput { rel_path: String, mtime_ns: i64, size_bytes: i64, headlines: Vec<HeadlineInput>, links: Vec<LinkInput> }`, `HeadlineInput { kind, level, position, byte_start, byte_end, todo_keyword: Option<String>, todo_done: Option<bool>, title, body, scheduled/deadline/closed (date/time), tags: Vec<String>, properties: Vec<(String,String)>, clock_entries: Vec<…>, parent_ordinal/children shape }`. Field set mirrors the schema columns exactly (migrations/0001_initial-schema.sql:74-253). These types are the contract `orgsidian-core` maps `Document` into.
- **`upsert_file(conn: &mut Connection, input: &FileIndexInput) -> Result<(), IndexError>`** runs the full per-file mutation **inside one transaction** (`conn.transaction()`): (1) if the file already has rows, emit the FTS `'delete'` command rows for its existing headlines **before** deleting them, in the mandated order (migrations/0001_initial-schema.sql:289-308) — `INSERT INTO fts_headlines(fts_headlines, rowid, title) VALUES('delete', id, old_title)` + same for `fts_content`/`body`, then `DELETE FROM headlines WHERE file_id=…`; (2) upsert the `files` row (mtime/size/indexed_at); (3) insert headlines (parent_id resolved to real rowids, same-file invariant upheld — migrations/0001_initial-schema.sql:139-146), tags, properties, clock_entries, links; (4) insert the paired `fts_headlines`/`fts_content` rows with `rowid = headlines.id`. The headline↔FTS pairing is **structural** (same function, same transaction) — never a convention a caller could forget (resolves the rowid-reuse landmine, deferred-work.md — the `AUTOINCREMENT` row). A synthetic `kind='preamble'` row carries `Preamble.text` (migrations/0001_initial-schema.sql:96-102).
- **`delete_file(conn: &mut Connection, rel_path: &str) -> Result<(), IndexError>`** performs the FTS-`'delete'`-then-`DELETE headlines`-then-`DELETE files` order in one transaction.
- **`file_is_unchanged(conn, rel_path, mtime_ns, size_bytes) -> Result<bool, IndexError>`** — the incremental skip predicate (compares the stored `files.(mtime_ns, size_bytes)`), the primitive that makes the cached fast-open (AC7) and resume-after-cancel cheap.
- **Quarantine path:** `quarantine_file(conn, rel_path, mtime_ns, size_bytes, reason: &str)` writes a `files` row with `quarantined=1, quarantine_reason=reason` and **no** headlines (satisfies the `quarantined=0 OR reason IS NOT NULL` CHECK and the "quarantined file has nothing to show = bug" contract — migrations/0001_initial-schema.sql:83-113). This is how a parser-errored file is recorded (LD-41).
- **`src/identity.rs` — index-identity guard** (resolves the `application_id`/foreign-file deferred rows). `pub const APPLICATION_ID: i32 = <stable magic, documented>;`. `stamp_application_id(conn)` sets `PRAGMA application_id` (on a freshly created index). `check_index_identity(conn) -> Result<IndexIdentity, IndexError>` reads `PRAGMA application_id` + `PRAGMA user_version` and classifies: `Ours` (application_id matches + user_version == 1), `Foreign` (application_id is 0 or unknown → not our file), `VersionMismatch` (ours but user_version ≠ expected → LD-13 rebuild trigger). This is invoked by the vault-index open path (AC4) to decide open-cached vs rebuild vs refuse — it does **not** edit `connection.rs::open()`.
- **`IndexError`** grows non-panicking variants as needed (e.g. `Sync`, `ForeignIndexFile`, `SchemaVersionMismatch`) on the existing `#[non_exhaustive]` enum, mirroring the `thiserror` shape. No `unwrap`/`expect`/`panic!` in committed non-test code; `println!` forbidden (use `tracing`).
- **`src/lib.rs`** re-exports the new surface (`sync::{upsert_file, delete_file, file_is_unchanged, quarantine_file, FileIndexInput, …}`, `identity::{APPLICATION_ID, check_index_identity, IndexIdentity}`) with a present-tense crate-doc sentence (no forward-looking prose — Dev Note 8).
- **FTS-staleness contract tests** (`tests/sync.rs`, resolves the "no test covers FTS staleness on UPDATE or DELETE" MED deferred row): after an `upsert_file` that **changes** a headline's title/body, the OLD term no longer MATCHes and the NEW term does; after `delete_file`, a MATCH for the deleted term returns no hit and does not raise `fts5: missing row`; a re-`upsert_file` at the same path with a rowid that SQLite may reuse does not surface a stale hit (the rowid-reuse scenario, driven against the shipped DDL). Real on-disk `TempDir` DB, spawn the `IndexWriter` first (it migrates), submit via `execute`. Anti-placebo (Story 1.9): removing step (1)'s FTS `'delete'` emission must make a staleness assertion fail; restore green and record in the Debug Log.

### AC3 — `orgsidian-vault`: recursive `.org` discovery, path canonicalization, orphan-temp cleanup wiring.

- **`src/path.rs`** (the FR-15 home — architecture.md:1058). `canonicalize_vault_root(path: &Path) -> Result<PathBuf, VaultError>` resolves the designated root once (`std::fs::canonicalize`), the single normalization site the path-identity deferred rows assign to Vault-open (deferred-work.md — the three coupled MED rows; owner: "the Vault-open story that first constructs the shared handle"). `scan_org_files(root: &Path) -> Result<Vec<PathBuf>, VaultError>` walks recursively (`walkdir`), yields files with a case-insensitive `.org` extension, **skips the `.orgsidian/` config dir** and any dotfile dir, and is deterministic (sorted) so progress counts and tests are stable.
- **Path meaning decision (owned here per the schema comment — migrations/0001_initial-schema.sql:63-69):** the index stores **vault-relative** paths (relative to the canonical root), separator-normalized to `/`. `to_rel_path(root, file) -> Option<String>` returns `None` for a non-UTF-8 name (which the caller quarantines/skips — resolves the `files.path TEXT` non-UTF-8 deferred row by an explicit skip-and-count, not a silent lossy rename). Case-folding on case-insensitive volumes is **not** applied (the on-disk case is stored); the residual two-spellings collision risk is documented, not fixed here (keep that deferred row open, downgraded — canonicalizing the root at open addresses the common case).
- **`clean_orphan_temp_files` wiring:** the vault-open path (whichever function AC4/AC3 designates as "open this vault") calls `atomic::clean_orphan_temp_files(vault_root)` once (the integration point named at `orgsidian-vault/src/lib.rs:8-9` and the atomic-write deferred rows at deferred-work.md — the `*.tmp.<pid>` residue). A non-fatal cleanup error is logged (`tracing::warn`), not propagated — cleanup is hygiene, not a gate on opening the vault.
- Unit/integration tests for `scan_org_files` (nested dirs, `.orgsidian/` skipped, non-`.org` ignored, deterministic order) and `canonicalize_vault_root` (symlinked root resolves) in `crates/orgsidian-vault/tests/`. No `unwrap`/`expect`/`panic!` in committed non-test code.

### AC4 — `orgsidian-core`: the scan orchestrator (walk → parse → map → batch-submit, incremental, cancellable, progress).

- **`src/index/mod.rs`** — the index façade (mirrors the `parser` façade at `lib.rs:23-28`), the only crate that names both `orgsidian_parser` and `orgsidian_index`. It owns the `Document` → `orgsidian_index::FileIndexInput` mapping (`src/index/map.rs`): every `Headline` field → its column, tags/properties/clock/links flattened, the preamble → the synthetic `kind='preamble'` row.
- **`src/index/scan.rs`** — `scan_vault(vault_root, index: &IndexHandle, cancel: &AtomicBool, progress: impl FnMut(ScanProgress))` where `ScanProgress { current: u32, total: u32, errors: u32 }` is a **plain core struct** (no `tauri`/`specta` dep in core beyond what `OrgError` already uses; the shell maps it to the `IndexProgress` event — Dev Note 5). Algorithm:
  1. `total = scan_org_files(root).len()` (vault).
  2. Iterate files. For each: compute `(mtime_ns, size_bytes)` via `std::fs::metadata`; if `file_is_unchanged` → skip (increment `current`, no write). Else read + `parser::analyze()` (CPU-bound → `spawn_blocking`, LD-16); on parse error → accumulate a `quarantine_file` op + increment `errors`; on success → map to `FileIndexInput` + accumulate an `upsert_file` op.
  3. **Checkpoint every 100 files** (configurable via `global.toml` per LD-42 — read the interval from `GlobalSettings`, default 100): submit ONE `IndexWriter::execute(|conn| { let tx = conn.transaction()?; for op in batch { op.apply(tx)?; } tx.commit()?; })` — i.e. **one SQLite transaction commit per checkpoint** (LD-42's coupled commit+progress), then invoke `progress(ScanProgress{current,total,errors})`. Batching per checkpoint (≤100 messages for a 1000-file vault) sidesteps the `WRITER_CHANNEL_CAPACITY=256` bulk concern (resolves that deferred row — the bulk writer submits ~10 messages, not 1000; document that batching, not a raised bound, is the fix).
  4. **Cancellation:** check `cancel.load(Acquire)` at each checkpoint boundary; on set, commit the in-flight batch, emit a final progress, and return `ScanOutcome::Cancelled { indexed, errors }`. Already-committed checkpoints are the retained partial index (LD-42). No new dep — `Arc<AtomicBool>` (tokio_util's `CancellationToken` is in the lock and an acceptable alternative if the dev prefers it; AtomicBool is the zero-dep default).
  5. **Resume / cached open** is implicit: a re-run skips every file whose `(mtime_ns, size_bytes)` already matches, so a killed-then-restarted scan resumes (committed files skipped) and an unchanged vault does ~zero write work (AC7). No separate checkpoint cursor is persisted; the `files` table IS the cursor.
- **`designate_vault(vault_root) -> Result<IndexHandle, OrgError>`** (domain fn the shell command calls): canonicalize the root (vault), resolve the index DB path in the OS data dir (index lives OUTSIDE the vault — LD-40, architecture.md:1192; derive a stable per-vault DB filename, e.g. hash of canonical root), `clean_orphan_temp_files`, open-or-create the index: `IndexWriter::spawn` (migrates) + `IndexPool::new`; run `check_index_identity` — `Foreign` → refuse with a distinct `OrgError`; `VersionMismatch` → drop + recreate (LD-13 rebuild); fresh create → `stamp_application_id`. Write the canonical root into `vault_meta` (key `vault_root`) and push it onto `GlobalSettings.recent_vaults` (most-recent-first, deduped, cap 10 — schema.rs:147-149) via `settings::write_global_settings`. Returns the handle the shell keeps in managed state.
- **`OrgError`** grows an `Index`-shaped path if needed (the `Index { reason }` variant already exists — architecture.md:748-749); a foreign-index refusal maps to a clear, actionable message (ux:291 — what happened / what was preserved / what to try).
- Integration test (`crates/orgsidian-core/tests/scan.rs`): a `TempDir` vault with N `.org` files (incl. ≥1 deliberately malformed) → `scan_vault` indexes N-errors files, quarantines the malformed one(s), `errors` count is exact; a second `scan_vault` on the unchanged vault does zero upserts (assert via a write-counter or unchanged `indexed_at`); a mid-scan cancel retains the committed prefix. No `unwrap`/`expect`/`panic!` in committed non-test code.

## Dev Notes

### 1. The LEAF rule forces the `Document`→rows mapping into `orgsidian-core`, not `orgsidian-index` (the central design decision)

The recon's instinct — "put the sync engine in `orgsidian-index/src/sync.rs`" — is right for the **SQL**, wrong for the **mapping**. `orgsidian-index` is a LEAF crate whose only permitted wrapper is `orgsidian-core` (deny.toml:193-194: `name = "orgsidian-index", wrappers = ["orgsidian-core"]`). Adding `orgsidian-parser` as a dependency of `orgsidian-index` would make the index crate a **second** wrapper of the parser leaf — which `parser`'s own allowlist (`wrappers = ["orgsidian-core"]`, deny.toml:189-190) forbids, and `cargo deny check graph` fails. So:

- `orgsidian-index::sync` takes **parser-agnostic input structs** (`FileIndexInput`, `HeadlineInput`, …) mirroring the schema columns. It knows SQLite and FTS5; it does not know `Document`.
- `orgsidian-core::index::map` does `Document` → `FileIndexInput`. Core already depends on `parser` (façade, lib.rs:23-28) and — after Task 1 — on `index`. It is the composition root (lib.rs:1) and the only place both are visible.

This is the same "the leaf ships the mechanism, the hub wires the domain" shape the whole crate graph is built on (architecture.md:1015-1028). It also keeps `orgsidian-index` unit-testable without a parser, and lets Epic 5's incremental re-index reuse `upsert_file`/`delete_file` unchanged (the architecture's `orgsidian-index::sync::incremental` — architecture.md:1121 — is this module; "incremental" = the `file_is_unchanged` skip + single-file upsert, which Epic 5's watcher calls per changed file).

### 2. Consume Story 3.5's writer/pool exactly as shipped; batch per checkpoint

`IndexWriter::execute<F>(&self, f: F)` where `F: FnOnce(&mut Connection) -> Result<(), IndexError> + Send + 'static` is the **only** write path (Single Writer Rule, LD-7/LD-14). The scan submits **one `execute` per 100-file checkpoint**, whose closure opens `conn.transaction()`, applies every batched op, and commits — this is LD-42's "SQLite transaction commit + progress UI update every 100 files" (architecture.md:1213) realized as one message, and it makes the `WRITER_CHANNEL_CAPACITY=256` bound a non-issue (a 1000-file scan sends ~10 messages, each awaiting its ack → natural backpressure). Do **not** submit one `execute` per file (1000 round-trips, and the per-file commit defeats the checkpoint durability model). The writer already `migrate`s once at `spawn` (sole migration site) — the pool's readers must never migrate (Story 3.5 Dev Note 5); construct the writer before any read.

`file_is_unchanged` / metadata reads happen on the orchestrator side before batching (cheap `stat`s), and `parser::analyze()` is CPU-bound → wrap the read+parse of each file in `tokio::task::spawn_blocking` (LD-16, architecture.md:408) so a 5000-line org file never stalls an async worker. The parser is lenient (LD-41) — `analyze` returns `Err` only on defensive internal errors that "never fire in practice", so most "errors" are actually the parser succeeding on garbage; decide quarantine by whether `analyze` returns `Err` OR (optionally) whether the tree contains ERROR regions — for this story, `Err` → quarantine is the contract (LD-41: "Parser returns error on file → mark quarantined").

### 3. FTS external-content pairing is a correctness landmine — make it structural (resolves 3 MED deferred rows)

The schema is emphatic (migrations/0001_initial-schema.sql:289-308): the two FTS5 tables are **external-content** over `headlines`, there are **no triggers**, and the sync engine MUST (1) write `('delete', rowid, old_text)` command rows **before** deleting/updating a headline, in the order FTS-delete → `DELETE headlines` → `DELETE files`, all in one transaction. Skipping step 1 doesn't just stale the index — a later MATCH returns a hit for a gone row and raises `fts5: missing row` / `SQLITE_CORRUPT`. Combined with `headlines.id INTEGER PRIMARY KEY` **without** `AUTOINCREMENT` (rowid reuse — deferred-work.md), a single missed `'delete'` row followed by a reinsert makes a query return a *different live headline's* body with no error. The mitigation the deferred row demands is exactly what AC2 mandates: the headline mutation and its FTS command row live in **one function, one transaction** — never a caller convention. `tests/sync.rs` proves it on UPDATE, DELETE, and rowid-reuse, with an anti-placebo drop of the `'delete'` emission (resolves "No test covers FTS staleness on UPDATE or DELETE" + the rowid-reuse row).

### 4. Path identity: canonicalize the root once, store vault-relative, skip non-UTF-8 (resolves the path-identity cluster)

Three coupled MED deferred rows (`DirtyBufferManager` keys on raw `PathBuf`; `files.path` stores whatever string; path-identity policy still open) all point at one question — "what does a path MEAN in this Vault" — whose owner they name as "Story 3.6 (Vault-open): it designates the Vault root, so it owns the normalization." This story answers it: canonicalize the root once (`canonicalize_vault_root`), store **vault-relative** paths normalized to `/`, and hand the same canonical form to the index (and, when Epic 5 wires it, the dirty-buffer/watcher). Non-UTF-8 filenames (legal on Linux/macOS, unrepresentable in `files.path TEXT` → `&str`) are **skipped and counted as errors** (quarantine), not lossily renamed — resolves that row explicitly. Case-folding on case-insensitive volumes is **not** applied (store on-disk case); the residual "two spellings pre-canonicalization collide" risk stays a downgraded deferred row (rename/move remap is separately Epic 5's — leave it open).

### 5. `IndexProgress` lives in the shell, not core — the tauri_specta boundary

`IndexProgress` must derive `tauri_specta::Event`, which is only available in `orgsidian-shell-app` (core has no `tauri`/`tauri_specta` dep, and must not gain one — it is the domain layer). So core's `scan_vault` reports progress through a **caller-supplied `FnMut(ScanProgress)`** with `ScanProgress` a plain core struct; the shell's `progress` closure constructs `IndexProgress { current, total, errors }` and emits it via the generated event handle. This keeps the tauri surface in one crate and lets `scan_vault` be tested in `orgsidian-core` with a plain counting closure (no tauri). Note `OrgError` already lives in core deriving `specta::Type` (architecture.md:748) — that's a `specta` edge, not a `tauri_specta` one; do not conflate them. The event is the app's **first** declared event: `collect_events!` is absent today (`mount_events` runs but registers nothing — recon), so adding `.events(collect_events![IndexProgress])` to `build_specta()` lights up the `events` object in the generated `tauri.ts`.

### 6. Index location, identity guard, and the cached-open / rebuild triangle

The index is a **derived** SQLite file that lives **outside** the Vault, in the OS data dir (LD-40, architecture.md:1192; LD-17) — never in `.orgsidian/` (that's authoritative settings, not derived data). Derive a stable per-vault DB filename from the canonical root (e.g. a hash) so re-designating the same folder finds the same DB. On open, `check_index_identity` (AC2) distinguishes three cases — this is the concrete form of LD-13's rebuild triggers (architecture.md:402):
- **Ours + user_version==1** → open cached; the incremental scan skips unchanged files → the epic's "<1s cached open" (mechanism scope).
- **VersionMismatch** (ours, wrong version) → drop + rebuild (LD-13 trigger a).
- **Foreign** (application_id 0/unknown) → refuse with an actionable `OrgError` rather than rewriting someone else's SQLite file's journal mode (the exact failure the `application_id` deferred row describes — deferred-work.md:245). `integrity_check`-on-startup (LD-13 trigger b) and the CLI `integrity`/`rebuild` surface are Story 3.7; this story ships the identity stamp+guard and the drop+rebuild-from-files path (which is just a fresh scan — free because the scan engine exists here).
