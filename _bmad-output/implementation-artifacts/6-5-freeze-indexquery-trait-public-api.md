## Intent

**Problem:** Stories 6.3/6.4 shipped `agenda::today`/`agenda::week` as plain, tested functions with no semver contract around them. Epic 7 (agenda extensions: `custom`, Today Dashboard) and Epic 8 (Search, Backlinks, Graph queries) are about to build on `orgsidian-index::query` — without a frozen, CI-enforced surface, either epic can accidentally reshape a signature the other (or the shell/core façade) already depends on, discovered only when something downstream breaks. Per the 2026-05-20 reconciliation (Party Mode P0, Amelia; Murat round-2 automation fix), the fix is to freeze the WHOLE v0.1 baseline surface — including the not-yet-built Search/Backlinks/Graph/Custom-Agenda signatures — now, and enforce it automatically with `cargo-semver-checks` rather than a manual review gate.

**Approach:** `crates/orgsidian-index/src/query/mod.rs` gains the `IndexQuery` trait: eight default-bodied methods (`agenda_today`, `agenda_week`, `agenda_custom`, `search`, `search_stream`, `backlinks_for_headline`, `backlinks_unlinked_mentions`, `graph_adjacency`), each wrapping the matching submodule free function, implemented by the zero-sized `DefaultIndexQuery`. `agenda::today`/`agenda::week` (Stories 6.3/6.4) are untouched. Four new submodules ship the REST of the frozen signatures as real, callable functions with STUB bodies (never `unimplemented!()` — see Design Notes): `agenda::custom` (Story 7.4's `CustomAgendaQuery` params), `search::{query, search_stream}` (Story 8.4's two-tier `SearchQuery`/`SearchResult`), `backlinks::{for_headline, unlinked_mentions}` (Story 8.6/Story 12.0's `Backlink`/`UnlinkedMention`), `graph::adjacency` (Story 8.10's `GraphScope`/`EdgeKind`/`GraphData`). Every new struct/enum is `#[non_exhaustive]` so later stories grow them additively. A shared `HeadlineId(i64)` newtype gives the new Backlinks/Search/Graph surfaces one typed identity. `crates/orgsidian-index/CHANGELOG.md` (new file) records the `Query API: v1.0` baseline. `.github/workflows/pr.yml` adds a `cargo-semver-checks check-release -p orgsidian-index` step, gated on a documented baseline-rev strategy (see Design Notes — the AC's literal `v0.1.0-alpha.x` tag does not exist until Story 6.10, which epics.md itself notes lands after Epic 7/8).

## Design Notes

- **Why the unbuilt queries are stub FUNCTIONS with real signatures, not trait-only declarations.** `cargo-semver-checks` (like SemVer itself) only inspects signatures — parameter/return types, trait method sets, `#[non_exhaustive]` markers — never function bodies. Shipping the real signature now, with a body that returns an empty result, means the eventual real implementation (Story 7.4, 8.4, 8.6, 8.10, 12.0) is a pure body edit that `cargo-semver-checks` sees as zero API change. That is what makes "Epic 7/8/12 land as semver-MINOR body additions, not breaking changes" true by construction. The bodies deliberately never `unimplemented!()`/`panic!()`: they are reachable through `IndexQuery`'s default methods (e.g. `DefaultIndexQuery.search(...)`) before their owning story lands, and a stub that can panic would be worse than no surface at all.
- **Why `AgendaItem` and `agenda::today`/`agenda::week` are untouched, including NOT retroactively marking `AgendaItem` `#[non_exhaustive]`.** This story's own CI gate diffs the post-freeze tree against the pre-freeze baseline (see the baseline-rev strategy below). Marking an already-public, already-exhaustive struct `#[non_exhaustive]` in the SAME commit that introduces the gate would itself register as a breaking change against that baseline — the freeze story would fail its own new check. `AgendaItem`'s future growth path is the AC's own documented escape hatch: a deliberate field addition is a semver-major change requiring an explicit CHANGELOG entry + reviewer override, exactly like any other post-freeze breaking change.
- **Why `HeadlineId` is a plain tuple struct, not `#[non_exhaustive]`.** Every other new type in this freeze is `#[non_exhaustive]` for field/variant growth room. `HeadlineId` is a single-field opaque row-id wrapper — there is no plausible future field to add — and, unlike the parameter/result structs, callers across crate boundaries (CLI arg parsing, the editor's cursor-headline lookup) need to construct one directly (`HeadlineId(42)`). A non-exhaustive tuple struct would make that impossible without a dedicated constructor function this story has no reason to invent yet.
- **Why `IndexQuery`'s methods take `&self, conn: &Connection, ...` instead of `impl IndexQuery for Connection`.** The more "ergonomic-looking" alternative — implementing the trait directly for `rusqlite::Connection` (`conn.agenda_today(today)`) — was considered and rejected: a trait-declared DEFAULT body for such a design would need `Self` to concretely BE `Connection` to call the submodule free functions, which defeats the point of a default body (it could never be generic). Taking `conn: &Connection` as an explicit parameter keeps every method's default body trivially callable regardless of what `Self` is, so `IndexQuery` gets real default-method growth-safety (a future new method can ship with a default body, non-breaking for any external implementor) rather than requiring every implementor to hand-write every method.
- **Why `IndexQuery` is not `dyn`-compatible.** `search_stream` returns `impl Iterator<Item = SearchResult>` (return-position-impl-trait-in-traits, stable since Rust 1.75) — an opaque type unnameable in a vtable. Nothing in the codebase needs `dyn IndexQuery` today (existing callers use the free functions directly); a caller wanting one polymorphic value uses `impl IndexQuery`/`DefaultIndexQuery`. Documented explicitly in the module doc-comment so a future story doesn't discover this by a confusing compiler error.
- **Why `SearchQuery` wraps a raw `text: String` instead of exposing parsed fields, and why it's a struct at all rather than a bare `&str` parameter.** The Story 8.4 AC's query-DSL (plain words, `"exact phrase"`, `#tag:value`, `file:path-glob`, `todo:STATE`) is parsed FROM the raw text by that story's own implementation — this story has no parser to expose fields from yet. A `&str` parameter can never grow (changing it to accept a struct later would itself be a breaking signature change), so freezing a `#[non_exhaustive]` struct now — even though it holds only `text` today — means Story 8.4 can add pre-parsed structured fields alongside the raw text without touching `query`/`search_stream`'s signature at all.
- **`--release-type minor` is required, not optional — the load-bearing finding of this story's live validation.** Every workspace crate is version-pinned at `0.0.0` (`[workspace.package] version = "0.0.0"`, Story 1.2 — no crate is published pre-v0.1, so nothing bumps it). Running `cargo semver-checks check-release --baseline-rev 59a5727 -p orgsidian-index` with no other flags against this story's own diff produced `Checking orgsidian-index v0.0.0 -> v0.0.0 (no change; assume major)` / `Starting 0 checks, 254 unnecessary` / `Checked 0 checks: 0 pass, 254 skip` — a SILENT NO-OP that still exits 0 and prints "no semver update required", because a same-version comparison makes the tool assume a major bump is intended, and a major bump permits any change so every lint is "unnecessary". Adding `--release-type minor` fixed this: `Checking ... (assume minor change)` / `Checked 196 checks: 196 pass, 58 skip` — the full major-breakage lint set actually runs. Confirmed both directions by deliberately breaking `agenda::today`'s signature (added a third parameter) and re-running: WITHOUT `--release-type minor` it still reported "no semver update required" (0 checks); WITH it, `function_parameter_count_changed` failed with `Summary: semver requires new major version: 1 major and 0 minor checks failed`, pinpointing the exact function and line. The change was reverted immediately after confirming the failure. Without this flag, the AC's entire enforcement goal ("fails the PR on any breaking change") would be silently false from day one.
- **`cargo-semver-checks` baseline-rev strategy (the AC's named ambiguity).** The AC's literal invocation, `--baseline-rev v0.1.0-alpha.x`, names a tag that does not exist — `git tag -l` on this worktree is empty, and `v0.1.0-alpha` is created by Story 6.10, which `epics.md`'s own "Note on execution order" states runs AFTER Epic 7 + Epic 8 despite Epic 6's lower number. Pinning the gate to that not-yet-existing tag now would make it a no-op for the ENTIRE window it exists to protect — precisely when Epic 7/8 are building on this frozen surface. Chosen instead: the baseline floats to "the tree immediately before this PR's commits" — `github.event.pull_request.base.sha` for a `pull_request` trigger, `HEAD~1` for a direct `push` re-run — the same "did THIS PR introduce a breaking change versus what's already on main" comparison `cargo-semver-checks` is designed around, requiring no pre-existing tag. A `TODO(Story 6.10)` comment in `pr.yml` flags the option to repin to the real tag once it exists, if the team later wants "diff against the last published release" semantics instead; either strategy already satisfies this story's AC (fails the PR on any breaking change to `query::*`). Not treated as a blocking decision-grade question because the floating-baseline default is strictly MORE protective than the literal AC wording (live from this PR onward, not only from v0.1.0-alpha onward) and requires no irreversible choice — a maintainer can repin later with a one-line change.
- **`cargo-semver-checks` version pin + nightly toolchain.** `taiki-e/install-action`'s `tool: cargo-semver-checks` entry is used unpinned (no `@x.y`) since this repo's other `taiki-e/install-action` tools (`cargo-deny@0.18`, `cargo-audit@0.22`) are pinned to specific minors the author could verify against a running instance; this environment DOES have live network access (confirmed by successfully building `cargo-semver-checks` from crates.io during Verification below), so — deviating from a pure "unverifiable, pin later" placeholder — the working invocation was validated end-to-end in this story's own sandbox rather than left as a guess. cargo-semver-checks needs rustdoc's unstable JSON output, which only nightly rustc produces: installed via a bare `rustup toolchain install nightly` (not `dtolnay/rust-toolchain@nightly`, which would flip the job's DEFAULT toolchain to nightly for every later step in the same job — including Step 14's `pnpm build`, which shells out to `cargo test ...export_bindings...` — a regression this story's CI diff must not introduce). `rust-toolchain.toml`'s `stable` pin stays the default; `cargo-semver-checks` invokes `+nightly` internally.
- **Residual: no bot enforces "major changes need reviewer override".** The AC's last clause ("semver-major changes... require explicit CHANGELOG bump + reviewer override") is honored by the CI gate FAILING the PR outright on a breaking change — a human must then either revert the change or deliberately override it (`--admin` merge, per the project's established branch-protection precedent, after adding the CHANGELOG entry by hand). This story does not add a bot that checks for a CHANGELOG entry before allowing the override; recorded here rather than in `deferred-work.md` since it is a deliberate, obviously-out-of-scope-for-one-story design point, not an accidental gap.
